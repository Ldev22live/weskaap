### 3.2 Specific Verifications

#### Building Entrance/Exit State
- `GameWorld` tracks `activeBuilding` (null when outside).
- `enterBuilding(Building)` sets `activeBuilding`, swaps obstacles/interactables to interior lists, moves Hero to interior spawn, resets platformer controller.
- `exitBuilding()` restores `activeBuilding = null`, swaps back to exterior data, moves Hero to `building.getExteriorReturnPosition()`.
- **Evidence:** `GameWorld.java` lines 754–795.

#### Exterior Position Preservation
- `exteriorHeroPosition` is a `Vector2` set to the Hero's position before entering a building.
- On exit, the Hero is placed at `building.getExteriorReturnPosition()`, which is derived from the entrance position minus `DOOR_RETURN_OFFSET`.
- **Note:** this is a *return position*, not a literal restore of `exteriorHeroPosition`. The variable is set but not currently used for re-entry. If the design intent was to return to the exact pre-entry spot, this is a gap.

#### Interior / Platformer Transition
- Inside a building, `GameWorld.update` calls `platformerController.update(...)` instead of top-down movement.
- Jump is bound to `SPACE`, `W`, or `UP` via `HeroController.isJumpRequested`.
- **Conflict risk:** `SPACE` is also the combat attack key. Inside a building, combat is disabled (`activeBuilding == null` check guards enemy AI and combat), so this does not currently conflict in practice.

#### Travel Between Areas
- `TravelPoint` is an `Interactable`. Interaction opens the travel menu via `TravelController.openMenu()`.
- `TravelController.requestTravel(AreaId)` validates destination (unknown, locked, not implemented, current area) and calls `requestAreaTransition` callback in `GameWorld`.
- `GameWorld.requestAreaTransition` fires `LEAVE_AREA` and `ENTER_AREA` quest events, then calls `loadArea`.
- **Evidence:** `GameWorld.java` lines 797–844.

#### Quest Progression
- `QuestController.handleEvent(QuestEvent)` iterates active quests and increments matching objectives.
- `QuestObjectiveType` includes `TALK_TO_NPC`, `ENTER_BUILDING`, `LEAVE_BUILDING`, `COLLECT_ITEM`, `REACH_LOCATION`, `ENTER_AREA`, `LEAVE_AREA`, `DEFEAT_ENEMY`.
- `GameWorld` emits events at the correct lifecycle points (enter/exit building, item collection, area transition, enemy defeat).

#### Dialogue State
- `DialogueController` tracks `currentDialogue`, `currentNode`, `active` flag.
- `DialogueStage` refreshes UI when node changes; options trigger `selectOption`.
- `DialogueOption` can carry `questId` and `objectiveId`, which are applied on selection.

#### Quest Rewards
- `QuestRewardService` supports `MONEY`, `ITEM`, and `STORY_FLAG` rewards.
- `QuestRepository` currently registers quests with empty reward lists.
- **Gap:** no quests actually grant rewards yet, so the reward pipeline is present but unverified in runtime.

#### Story State
- `StoryState` is an `EnumSet<StoryFlag>`.
- It is passed to `QuestRewardService` and can be set via story-flag rewards.
- Not directly read by gameplay code yet beyond rewards.

#### Ally State
- `Ally` has `RECOGNIZED` and `ALLY` relationship states.
- Rosebank friend NPC interaction calls `rosebankFriendAlly.establishAlliance()`.
- `AllyTest` verifies state transition.

#### Camera Behavior
- `IsometricCamera` switches between `ISOMETRIC` and `PLATFORMER` modes based on `GameWorld.getCameraMode()`.
- Constants for distance/height/zoom are hard-coded.
- No world-bounds clamping or collision avoidance.

#### 3D Rendering
- `WorldRenderer3D` uses libGDX `ModelBatch`, `Environment`, `DirectionalLight`.
- All visuals are colored boxes: ground tiles, roads, obstacles, buildings, NPCs, items, enemies, attack, interior platforms.
- Deprecated API warning noted above.

#### Interaction Prompts
- `MainGameScreen.updateInteractionPromptPosition` projects the current interactable's world position to screen space using `WorldCoordinateConverter.to3D(..., 80f)` and `camera.project`.
- `InteractionPrompt` renders a bubble at that screen position.

#### Combat / Death Behavior
- Unchanged from earlier milestones. Combat only runs when `activeBuilding == null` and Hero is alive.
- Dead Hero cannot move or interact; enemies stop chasing.

#### Inventory / Equipment
- Hero starts with `Basic Sword` and `Leather Armour` equipped.
- `I` toggles inventory text; `H` uses a Healing Potion.

### 4.2 Crash Log Analysis

#### hs_err_pid11180.log
- **JVM:** Eclipse Temurin 21.0.11+10
- **Error:** `Out of Memory Error (arena.cpp:168)` — native memory allocation (`malloc`) failed for C2 compiler arena (`Chunk::new`).
- **Thread:** `C2 CompilerThread0`
- **Command line:** Gradle daemon (`org.gradle.launcher.daemon.bootstrap.GradleDaemon 9.6.1`) with `-Xms512M -Xmx1G`.
- **Implication:** The Gradle build daemon ran out of native (not Java heap) memory while JIT-compiling. This is a **build-time/tooling OOM**, not a game runtime crash.
- **Relation to 3D renderer:** None directly. It occurred during Gradle compilation.

#### hs_err_pid29848.log and hs_err_pid35920.log
- **JVM:** Eclipse Temurin 21.0.12.1+1
- **Error:** Same `Out of Memory Error (arena.cpp:168)` in `C2 CompilerThread`.
- **Command line:** Eclipse JDT Language Server (`org.eclipse.jdt.ls.core.id1`) launched by the Devin/VS Code Java extension (`redhat.java`), with `-Xmx2G`.
- **Implication:** IDE language-server OOM during Java compilation/analysis. Also **tooling**, not game runtime.

#### replay_pid29692.log / replay_pid33936.log
- These are "replay" logs generated alongside the JDT LS crashes (same PIDs 29692 and 33936).
- They are binary/text replay data used for JVM crash reproduction and are very large.

### 4.3 Verdict on Crashes
- **No evidence that LWJGL, OpenGL, or the new 3D renderer caused any crash.**
- All crash logs point to **JVM C2 compiler native-memory exhaustion** under tooling (Gradle daemon / Eclipse JDT LS) on a 16 GB Windows 11 machine.
- This is a **build/IDE environment risk**, not a game-engine blocker.
- Recommended action: remove the two tracked `replay_pid*.log` files from Git (they bloat the repo), and consider increasing system available memory or reducing concurrent tooling memory pressure. Do **not** change game rendering code based on these logs.

### Key Architectural Observations
1. `GameWorld` is a **facade, coordinator, renderer, and state holder** all in one class.
2. It directly **mutates lists** that belong to multiple subsystems (`exteriorObstacles`, `buildings`, `exteriorInteractables`, `worldItems`, `enemies`) during area loading.
3. The **legacy 2D `render()` method** and the **3D `render3D()` path** both live in the same class. `MainGameScreen` currently only calls `render3D`, making the 2D path dead code.
4. `GameWorld` is responsible for **too much UI text formatting** (`getInventoryText()`, `getQuestLogText()`). These are presentation concerns.
5. Area data (obstacles, buildings, NPCs, enemies, items) is **hard-coded inside `GameWorld`**. This is the biggest scaling blocker.

### Safe Refactoring Map (do not change yet)
A future refactor should split `GameWorld` into:
- `AreaLoader` / `AreaManager` — owns `AreaRegistry`, loads/unloads areas, emits enter/leave events.
- `WorldRenderer` — owns `ShapeRenderer` and `WorldRenderer3D`, decides which to use.
- `InteractionSystem` — finds nearest interactable and dispatches interactions.
- `CombatSystem`, `EnemyAISystem`, `LootSystem`, `ConsumableSystem` — thin coordinators over existing controllers.
- `GameState` / `WorldState` — read-only snapshot of active lists for UI/rendering.

## 7. Tiled Pipeline Assessment

### 7.1 Assets Inspected
- `assets/retreat_location.tmx`
- `assets/retreat_placeholders.tsx`
- `assets/weskaap_tiles.png` (320x32 PNG, 10 tiles of 32x32)

### 7.2 Current TMX Contents
- **Map dimensions:** 50 x 50 tiles
- **Tile size:** 32 x 32 pixels
- **Orientation:** Orthogonal (not isometric)
- **Layers:**
  1. `Ground` — all zeros (empty)
  2. `Roads` — two horizontal road strips (tile id 2)
  3. `Buildings` — two building footprints (tile id 4) plus entrance markers (tile id 7)
  4. `Environment` — four tree placeholders (tile id 6)
  5. `Collision` (objectgroup) — 4 rectangles (2 buildings, 1 shop, 1 fence)
  6. `Objects` (objectgroup) — entrances, landmarks (Table Mountain, School), vehicle
  7. `Spawns` (objectgroup) — player spawn point

### 7.3 Is the TMX Loaded by the Game?
**No.** Searching the codebase reveals no `TmxMapLoader`, `TiledMap`, or `MapRenderer` usage. The game still constructs the Retreat world entirely from hard-coded rectangles and lists in `GameWorld`.

### 7.4 Coordinate/Scale Mismatch
- The TMX is 32 px/tile and 50x50 tiles = 1600 x 1600 pixels.
- The in-game `GameWorld.WIDTH / HEIGHT` is 3200 x 2400 world units, and the 3D renderer uses `TILE_SIZE = 160f`.
- A direct 1:1 mapping between TMX pixel coordinates and world units is **not currently possible** without a defined scale factor.

### 7.5 What Is Missing Before Tiled Can Become Authoritative
1. **TMX loader integration** — add `TmxMapLoader` and load `retreat_location.tmx` for the active area.
2. **Coordinate transform** — define and implement world-unit ↔ Tiled-pixel conversion.
3. **Collision layer consumption** — read `Collision` objectgroup rectangles into `Rectangle` obstacles.
4. **Building layer consumption** — parse building footprints and entrance markers into `Building` instances.
5. **Spawn layer consumption** — read `PlayerSpawn` object into Hero starting position.
6. **Object/NPC layer consumption** — create `PrototypeNpc`, `TravelPoint`, `PrototypeItem`, `PrototypeEnemy` from Tiled objects/properties.
7. **Layer rendering** — decide whether to render the TMX directly (orthogonal renderer) or continue using the 3D box renderer driven by Tiled data.
8. **Isometric vs orthogonal mismatch** — the TMX is orthogonal while the game is isometric. Either convert the TMX to isometric orientation or keep Tiled as a data-only source and render in 3D separately.

### 7.6 Verdict
The TMX is a **structural sketch** with placeholder tiles, object layers, and spawn/collision data. It is **not yet functional** in the game. It can eventually replace the hard-coded Retreat world, but that requires a loader, coordinate mapping, and a decision on whether Tiled drives rendering or only data.

## 9. Recommended Next Milestone

**Recommendation: M12 — "Area Data & Tiled Loader Foundation"**

Rationale:
- All M11 gameplay systems (camera, buildings, travel, dialogue, quests, rewards, story, ally, economy) are present and pass tests.
- The single biggest architectural risk is the hard-coded world data inside `GameWorld`.
- A TMX map and tileset already exist, providing a ready data source.
- Loading the TMX will force the project to define the world-unit ↔ Tiled-pixel contract, which is a prerequisite for replacing `GameWorld`'s hard-coded Retreat setup.

### Suggested M12 Scope
1. Implement a `TiledAreaLoader` that can read `retreat_location.tmx`.
2. Parse `Collision`, `Objects`, `Spawns`, and `Buildings` layers into the existing domain objects (`Rectangle`, `Building`, `PrototypeNpc`, `TravelPoint`).
3. Keep the 3D box renderer; feed it from Tiled-derived data instead of hard-coded values.
4. Add a coordinate-scaling utility (e.g., `TiledCoordinateConverter`) and document the chosen scale.
5. Add unit tests for the loader and coordinate conversion.
6. Leave architecture refactoring of `GameWorld` for M13 (after data is loaded externally).

### Why Not Refactor `GameWorld` First?
Refactoring `GameWorld` while its data is still hard-coded is possible, but it is safer to **externalize the data first** because:
- The loader defines the real boundaries between "data" and "runtime state".
- Refactoring after loading gives each new system a clear input contract.
- It avoids re-implementing hard-coded construction logic inside a new architecture.
